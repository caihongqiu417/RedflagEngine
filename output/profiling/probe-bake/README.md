# 灯光工作室的命令行烘焙

在仓库根目录运行 `python tests/check_probe_baker.py`。需要 Windows、已经生成的 Debug/x64 RedflagForge、支持 Vulkan 的显卡，以及 Python 的 PyYAML、pywin32。脚本会列出临时目录。场景、模型和编辑器运行所需的文件都复制到那里，GUI 也在独立桌面打开。要保存一次运行的读数，可加 `--report tmp/probe-check.json`。

测试从灯光工作室出发，在白墙前加入一盏强度为 4 的点光源。在同一块显卡上启动两个独立的命令行进程，再在普通编辑器中按 Ctrl+Shift+B。每次比较前先移走上一份结果，要求三个进程重新算出的整份文件逐字节相同。这里比较的是同一程序、同一显卡的可重复性。换显卡或改过着色器，应重新测量。

## 只选中灯牌，也改变了探针文件

2026 年 11 月 22 日第一次在 NVIDIA GeForce RTX 5070 Ti Laptop GPU 上运行时，两个命令行进程都生成了以 `b85ee814` 开头的 SHA-256。打开编辑器，等灯牌属性出现，保持鼠标不动，只按烘焙快捷键，结果却以 `207e381b` 开头。这一版程序的 SHA-256 以 `1891e324670a` 开头。两份探针文件都是 96,792 字节。跳过文件头，依次查看每个探针方向的红、绿、蓝亮度，三个通道分别有 1,600、794、492 处发生变化。

场景用弧度保存旋转，属性面板用度显示。文件写的 1.28 弧度读成单精度数是 1.2799999713897705。旧版每画一次面板，即使读者没动控件，也把显示用的角度乘回弧度，灯牌的实际旋转变成了 1.28000009059906。灯牌转过这么小的角度，人眼很难察觉，但由它算出的三角形顶点已经变了，编辑器会判定原来保存的光照过期。把副本中灯牌的旋转手动改成后一个数，再用旧版命令行烘焙，整份文件与旧版 GUI 的结果逐字节相同。

现在面板先用一份临时的角度显示数值。读者拖动哪根轴的控件，才把那根轴换回弧度。修正后，同一份场景的两次命令行烘焙和快捷键烘焙结果一致。[属性面板的实现](../../../Redflag/src/Redflag/Scene/Panel/SceneHierachyPanel.cpp) · [完整校验值与各用例退出码](cli-check.json)

正式版本已重新烘焙随项目提供的灯光工作室和浴室。两个场景文件及各自保存的渲染设置逐字节保持一致，每间房的光照文件为 96,792 字节。用编辑器重新打开，关掉 TAA，房间在面板大小固定后的 47 帧里只重画一次。若沿用修改光线求交之前的旧文件，灯光工作室会重新计算 32 帧。[两份随场景交付的文件](shipped-scenes.json) · [工作室的重开记录](../navigation-light/baked-Light-Studio.json) · [浴室的重开记录](../navigation-light/baked-frames.json)

## 实际改灯或材质

每个探针分六个方向，每个方向各测红、绿、蓝，504 个探针一共给出 9,072 个颜色读数。每项测试只改表中这一处，再和第一次烘焙比较。计数来自文件中解出的浮点数，不包含文件头与射线距离。

| 场景改动 | 变化的颜色读数 |
| --- | ---: |
| 关闭多次漫反射 | 8,784 |
| 白墙的三个底色分量从 0.78 降到 0.05 | 8,631 |
| 点光源强度从 4 调到 32 | 8,631 |

最后保留强度为 32 时的烘焙。把灯牌模型改成不存在的文件，程序返回 1，日志给出缺少的模型路径。再故意让场景的 YAML 列表缺一个右括号，程序也返回 1，并给出解析出错的行列。两次失败之后，探针文件仍与强度为 32 时逐字节相同。所有用例都在运行前后核对了场景和渲染设置的原始字节。[复现脚本](../../../tests/check_probe_baker.py)
