# 查源码和修改代码的实际用量

这次请模型修改 Redflag 的线程任务系统。假设正在录制一段游戏，两个工具先后调用了 `Trace(true)`。第一个工具已经记下来的任务时间，在第二次调用后消失了。另一个任务在线程里尚未结束，稍后完成时，它的时间也丢了。第一道题要求两者都能留下，同时让下一次录制确实从头开始。第二道题给主线程加工作量限制。比如游戏这一帧只打算执行一个已就绪的任务，就可以调用 `Pump(1)`，下一帧接着做。现有的 `Pump()` 仍要能照旧使用。

每道题都从独立的 Git 副本开始。模型可以用普通文本检索和读取源码（表中的「文本」），也可以在同样的工具上增加项目的 API 索引（「索引」）。此外我们测了编辑器里常见的另一种用法：开发者已经选中了这个方法，两组各用自己的检索工具找到声明、定义和调用位置，再把相同范围的源码交给模型。前一种用法最多对话十轮，后一种最多四轮。同组的任务原文与系统指令一致。自选工具时，第一轮会列出本组可用的工具；选中方法时，第一轮会附上各自检索所得的材料。因此发给服务的整个请求随工具而异。每次送出的材料、模型实际改的源文件、编译器返回的错误，以及调整后的代码都能在记录里逐轮核对。

## 先看一次修改

在编辑器已选中 `Trace` 的条件下，Qwen2.5-Coder-7B 用文本检索找到源码。它第一次提交的代码仍会丢掉历史任务，测试返回了 `repeating Trace(true) lost a completed or in-flight job`。第二次，它把清空记录和更新录制编号移到从关闭切到开启的位置。原生测试让工作线程停在一个可以控制的等待点，等主线程再次开启记录，再让任务完成。结果同时收到了之前完成的任务和这次刚结束的任务。另一起录制前，测试还专门留下一个跨两次录制的任务，确认它没有混进去。两次请求共用了 1,079 个输入 token、203 个输出 token。模型还改动了一行声明的缩进，补丁里保留了这处多余的改动。[改前的测试](example/trace-before.txt) · [第一次修改后的测试](example/trace-retry.txt) · [实际补丁](example/trace.patch) · [第二次修改后的测试](example/trace-after.txt)

另一局换用项目索引，返回正确的 `JobSystem.cpp:226`，还列出了调用者、项目测试以及测试启动脚本。模型却把命名空间和类声明塞进已有类的内部。再次编译后，错误信息也跟着进入后续请求。四轮合计用了 7,631 个输入 token、863 个输出 token，最终仍编译失败。检索找到正确位置和交付能运行的改动，在这里是两件可以单独测量的事。对应记录在原始包的 `coder/trace-context-6-selected-cpp/`。[逐轮请求、回执和测试](transcripts.zip)

| 已选中方法 | Trace | 文本 | 是 | 2 | 1,079 | 203 | 1,282 |
| 已选中方法 | Trace | 索引 | 否 | 4 | 7,631 | 863 | 8,494 |
| 已选中方法 | Pump | 文本 | 否 | 4 | 4,064 | 516 | 4,580 |
| 已选中方法 | Pump | 索引 | 否 | 4 | 5,144 | 526 | 5,670 |

| 自选工具 | Trace | 索引 | 否 | 10 | 10,891 | 499 | 11,390 |
| 自选工具 | Pump | 文本 | 否 | 10 | 18,460 | 801 | 19,261 |
| 自选工具 | Pump | 索引 | 否 | 10 | 18,264 | 1,081 | 19,345 |

7B 的八次尝试中，一次通过了行为检查。其余七次的补丁和错误也保留了。尤其是自选工具的 Trace：索引组用了 11,390 token，文本组用了 14,358 token，两组交上来的代码都没通过。用这两个数去计算「完成修复节省了多少」就失去了可比性。

正式组、早期预试和中断共保留了 29 局、178 次服务器回执。总输入 221,563 token，总输出 13,458 token，所有回执都带有用量。

每行的输入与输出都是服务器逐次返回的 `usage.prompt_tokens` 和 `usage.completion_tokens` 之和。模型第一次编辑、编译错误进入下一次请求、反复查同一处，都算在内。重复出现的历史消息会再计一次。服务报告命中前缀缓存的输入另列在 CSV 的 `cached` 列。这个口径量的是交互文字量，不能从它直接换算电费、响应时长或商业 API 账单。没有通过原生测试的尝试仍然列在表中，比较完成同一修改要同时看是否通过。[每次试验的完整计数](runs.csv)

## 核验与复跑

测试从 `bb1f5e1dba32576ec122308f6473eed902e2a876` 检出引擎源码、调用者与文档，并把同一份 API 索引存入每个临时 Git 副本。正式 7B 对照各组开始时 Git 树均为 `eda1d81b0a02333b17e4f19b4884b51ece0ae28e`。开发者的工作区和它正在编辑的任务系统不会被实验改写。编译器通过只读的公共目录取 vendor 头文件；旧版本未跟踪的 `Instrumentor.h` 在两组里使用相同的文件。索引在预试和正式试验之间重新生成过，快照包保留两份；同一对照的两边使用同一份。正式组的索引 SHA-256 是 `448fd394a25b845c389f7f563e14fdc13e2434f48c668d17e8c758f13262b6c6`。[实际使用的检索程序、索引与依赖快照](lookup-snapshot.zip)

原生测试直接编译各自副本里改过的 `JobSystem.cpp`。在第二道题，测试还把旧方法赋给 `void (JobSystem::*)()` 类型的成员函数指针。只给新参数设置默认值，虽然普通的 `jobs.Pump()` 看起来还能调用，但原有函数类型已经改变，这个测试能查出来。它还会检查刚提交的子任务是否会提前执行、零预算是否执行了工作，以及从工作线程调用时能否正确报错。模型能读引擎和既有项目测试；这组独立检查由实验脚本编译执行。[C++ 验证程序](../../../tests/fixtures/JobContextTasks.cpp) · [实验脚本](../../../tests/bench_dev_context.py)

在 Windows 仓库根目录运行下面的 PowerShell。需要 Git、ripgrep、Python、MSVC C++ 工具和项目的 vendor 依赖。先解开索引快照，再启动提供 OpenAI 兼容 `/v1/chat/completions` 及 llama.cpp `/props` 的本机服务。正式组使用 llama.cpp `b10887-4ea6d1bb6`，Q4_K_M 权重，上下文 8,192，温度 0。预选方法组的种子是 47，自选工具组是 48，单轮最多输出 550 token。权重文件 SHA-256 是 `509287f78cb4d4cf6b3843734733b914b2c158e43e22a7f4bf5e963800894d3c`。[作者公布的 7B 模型与权重](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct-GGUF/tree/13fb94bfda8c8cf22497dc57b78f391a9acb426a)

```powershell
# 解压的目录里包含真正运行过的 CLI 和 HTML 索引。
Expand-Archive output/validation/dev-context/lookup-snapshot.zip tmp/context-lookup
$common = @("--endpoint", "http://127.0.0.1:18186/v1",
            "--model", "Qwen2.5-Coder-7B-Instruct",
            "--cli", "tmp/context-lookup/dev_context.py",
            "--index", "tmp/context-lookup/index.html",
            "--output", "tmp/context-rerun")
foreach ($taskName in "trace", "pump") {
    foreach ($method in "classic", "context") {
        python tests/bench_dev_context.py @common --mode $method --task $taskName --iteration 6 --selected --cpp --turns 4
        python tests/bench_dev_context.py @common --mode $method --task $taskName --iteration 7 --turns 10
    }
}
python tests/summarize_dev_context.py tmp/context-rerun
```

原始包以模型、任务、检索方式和轮次建目录。`01-request.json` 是实际送出的消息，`01-response.json` 含生成文字及服务端计数，`01-tool.txt` 是工具的完整结果。`before-test.txt` 是未修改时的检查结果，`model.patch` 是这一局结束时模型留下的实际 Git 差异；空补丁表示未留下改动。若要独立核验统计，把原始包解到新目录，执行最后一条汇总命令并将目录换成解压处即可。两道题都出自同一个类，且只采一次固定种子，未覆盖跨模块设计、大仓库迁移或其他模型。普通检索也能很快定位这两个命名清楚的方法。
